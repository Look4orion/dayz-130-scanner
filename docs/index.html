DayZ Mod Scanner

Checks a mod's scripts for known breaking changes on the current DayZ stable version (1.30). It's kept up to date: when Bohemia opens a new experimental version, the scanner adds its changes, so you can see what will break before it reaches stable.

Your files never leave your computer. The scan runs in this browser tab and nothing is uploaded: the page can't send data anywhere except a visit counter (GoatCounter, no cookies), which records only that the page was opened or a scan was run, never anything about your files. Once loaded, the scanner works offline.

Drop mod folders or .pbo files here

A mod folder is the one with an Addons folder inside (@MyMod, or a Workshop number folder). You can drop several mods, or a whole folder of mods, at once. The mod folders in DayZ\!Workshop are links, which browsers can't open: drop the mod's Addons folder instead, or its real folder in steamapps\workshop\content\221100.

Reading the results

break Breaks on 1.30
Code 1.30 will not compile or will silently skip: overrides of methods that were removed or changed, name clashes with methods vanilla added, script folders written with backslashes that other code needs (1.30 loads none of their scripts, with no error), Workbench classes used outside #ifdef WORKBENCH (Workbench-only since 1.30.164200), vector.Cross() (removed again in 1.30.164200), a variable named like a class from another scanned mod (with both loaded: "Variable name already used as type name").
risk Check by hand
Uses something 1.30 removed or changed, where the scanner can't tell for sure from the name alone: menus taking global input focus with ChangeGameFocus (no device), script folders written with backslashes whose code nothing else needs (it still compiles, but what they do is lost), backslash script paths into another mod's folder used for optional support (#ifdef), methods 1.30 made protected, version gates like #ifdef DAYZ_1_30 that switch off again on 1.31, version gates in 1_Core scripts (the version defines aren't set there yet, so they always take the "not defined" branch), overrides of obsolete methods 1.30 no longer calls (they compile but never run), calls to obsolete methods 1.30 left empty (they do nothing).
info Good to know
Still works, but behaves differently on 1.30: CreateInInventory refusing items that don't fit, obsolete methods 1.30 still calls, overrides of obsolete methods whose replacement the mod also overrides, car headlight overrides 1.30 no longer calls, backslash script folders that are empty or hold only empty classes.
exp On the experimental build
While Bohemia has an experimental build open that is newer than stable, results also get "exp" grades (break, risk and info, as above) for what that build changes compared with stable: overrides of methods it removes or changes, names it adds that clash with the mod's methods, classes and members it removes, and methods it newly marks obsolete. With no newer experimental build open, results are for stable only.

What it can't tell you

  • A clean result means no known breaker was found, not that the mod works. It reads code; it doesn't run it.
  • It matches by name. A mod's own field or class that happens to share a name with something vanilla removed shows up as a "check by hand" hit. Read each hit before reporting it to an author.
  • Config is not checked (for example, 1.30 needing a _Ruined class for every car wheel).
  • Code under a mod's own #ifdef is checked both ways, as if the define could be on or off.
  • Mods that reference each other: drop them together, so names one mod defines count as known for the others.

Compares against an index of vanilla class and method names built from the game's own scripts: the current stable build and, when one is open, the newer experimental build. It is updated for each new build. The same scanner also runs from the command line: source and instructions.
